Concerns:

1. Gap cells contradicted by cathar, which another branch found (Critical, blocking). Framework: inversion; Socratic probing. 02d names cathar (MIT OR Apache-2.0, confirmed from both licence files) as the closest RX-like suite and says its code can be ported. Its source and README have permissive versions of modules 02a and 02b call gaps: `deplosive` (against 02a "Yes, for permissive code"); `dewow.rs` (against the Wow & Flutter gap); `rebalance.rs` (long-term spectrum match to a reference, against the EQ Match gap); `decrackle.rs` (against "no permissive classical code"); `adehum.rs` (against "no audio-specific adaptive repo"); `derustle` (against 02b's De-rustle gap); `dewind` (against "No open code"); `breath` (where 02b requires a 35 MB model). 02a also states no search routes for its De-plosive, Wow & Flutter, adaptive Phase and EQ Match gaps; only Mouth De-click names three routes as the frame requires. Why it matters: the "which are gaps" column and 02b's model choice for Breath Control rest on false facts; the 2026-09-12 receipt saw the same pattern ("no read-only flag" was false). What to do: re-map every gap cell against cathar's module list; several of its methods are naive (dewind is only a 4th-order high-pass), so the honest cell is "permissive baseline, naive", not "gap"; add cathar beside ffmpeg as a baseline in the RX harness.

3. The optimistic shortcut: the C++ core was recommended without counting what has to move into C++ (High, blocking). Framework: pre-mortem. 02a to 02d design numpy modules and 02d recommends a "pure numpy/scipy" runner; 02e recommends a C++ core but ports only "the STFT core". The repair modules (AR De-click, A-SPADE, WPE, MDF) stay in numpy, which by 02e's own finding cannot run inside a plugin, so the plugin would get an STFT and no repair DSP. "Keep the numpy version as the test oracle" means two implementations, the same drift cost 02e gave for rejecting option (c). Nobody counted the modules to port, estimated the effort, or said whether cumple's meters (bs1770, truepeak, VAD) must also exist in C++. Nobody connected 02d's cathar to 02e's language question: cathar is a Rust core that already holds most of the build-1 algorithms under MIT or Apache, which weakens 02e's case against option (b). Why it matters: build 1 (numpy De-click and De-clip) would be written, then rewritten. What to do: before Victor decides the order, 04 must choose between a compiled core from module 1 onward; numpy now with the plugin as a thin ARA front end to an out-of-process engine (the RX Connect pattern, which 02e cites); or a Rust core seeded from cathar; costing each path in module counts, estimates labelled.
